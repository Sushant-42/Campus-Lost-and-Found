## Answers to Assignment Questions

### 1. Your status map: every endpoint, its success status, and the status for each failure
* **`POST /items`**: Success **201 Created**. Failures: `400` (Malformed JSON), `401` (Unauthorized), `422` (Validation Error), `429` (Rate Limit Exceeded).
* **`GET /items`**: Success **200 OK**. Failures: `406` (Not Acceptable Accept header).
* **`GET /items/{item_id}`**: Success **200 OK** (or **304 Not Modified**). Failures: `404` (Not Found), `406` (Not Acceptable).
* **`PATCH /items/{item_id}`**: Success **200 OK**. Failures: `404` (Not Found), `409` (Illegal State Transition), `412` (Precondition Failed / ETag mismatch).
* **`POST /items/{item_id}/claim`**: Success **200 OK**. Failures: `404` (Not Found), `409` (Already Claimed).

### 2. Your type catalogue: the stable string for each failure and what triggers it.
* `malformed-request`: Triggered when the request body is not valid JSON (`400`).
* `unauthorized`: Triggered when the Authorization bearer token is missing or invalid (`401`).
* `validation-error`: Triggered when required body fields are missing or invalid (`422`).
* `item-not-found`: Triggered when requesting or modifying an item ID that does not exist (`404`).
* `illegal-transition`: Triggered when attempting an invalid status workflow transition (`409`).
* `item-already-claimed`: Triggered when attempting to claim an item that is no longer in `reported` status (`409`).
* `precondition-failed`: Triggered when an `If-Match` ETag header does not match the current resource state (`412`).
* `rate-limit-exceeded`: Triggered when exceeding 5 requests per 60 seconds per token (`429`).
* `not-acceptable`: Triggered when requested `Accept` header cannot be produced (`406`).

5. Which endpoints are safe to retry, and which status codes tell a client so? One line on why each.
GET /items, GET /items/{item_id} are safe to retry because they are idempotent read-only operations that alter no server state.

Status codes 429 Too Many Requests and 503 Service Unavailable tell a client it is safe to retry after a delay (via the Retry-After header) because the failure is transient, whereas 4xx client errors (except 429) should not be retried without modifying the request.

6. Where did you map an internal error to a clean client error, and what did you hide from the caller?
Internal upstream database or gateway connection exceptions are caught in try/except blocks and mapped to clean 503 Service Unavailable or 500 Internal Server Error Problem Details responses. This successfully hides raw stack traces, internal database table structures, and internal server paths from the caller.
